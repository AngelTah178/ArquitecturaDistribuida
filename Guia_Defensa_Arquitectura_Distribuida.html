Proyecto: Arquitectura Distribuida y Sincronizada entre MongoDB Atlas y PostgreSQL Neon

Universidad: UPQROO (Ing. en Software)
Materia: Bases de Datos en la Nube (7° Cuatrimestre)

Cloud: 3 Clústeres MongoDB Atlas + Neon PostgreSQL Serverless

1. Resumen Ejecutivo de la Arquitectura

El sistema implementa un modelo de Persistencia Políglota Híbrida. Resuelve el problema de escalabilidad en sistemas de alto tráfico mediante dos propósitos específicos:

  • Almacenamiento Transaccional NoSQL (Ingesta Rápida): 3 Clústeres distribuidos de MongoDB Atlas en AWS que reciben órdenes de compra desnormalizadas (con clientes y productos anidados en formato JSON).
  • Enrutamiento y Balanceo Dinámico (FastAPI): Clasificación y aislamiento de tráfico mediante particionamiento horizontal (*sharding* lógico) según la concurrencia de clientes.
  • Almacenamiento Analítico SQL (Reportes y BI): PostgreSQL en Neon Cloud con un esquema normalizado en Tercera Forma Normal (3FN) para reportes financieros y consistencia relacional.
  • Sincronizador ETL Diferencial: Tarea programada cada 3 minutos (APScheduler) que extrae documentos pendientes, los transforma a 3FN y los carga de forma idempotente en PostgreSQL.

A. Dónde se levanta la API y los servicios (backend/main.py)

Muestra el manejador del ciclo de vida asíncrono (lifespan):

@asynccontextmanager
async def lifespan(app: FastAPI):
    # 1. Conecta con los 3 clústeres de MongoDB Atlas
    mongo_manager.connect_all()
    # 2. Conecta con PostgreSQL Neon
    postgres_manager.connect()
    # 3. Registra el event loop en el controlador de bots
    simulator_controller.set_loop(asyncio.get_running_loop())
    # 4. Inicia el cron periódico del ETL (cada 3 minutos)
    sync_scheduler.start()
    # 5. Despierta 3 bots concurrentes por defecto
    simulator_controller.set_bots_count(3)
    yield
    # Apagado ordenado
    simulator_controller.stop_all()
    sync_scheduler.stop()

4. El Pipeline ETL y Consistencia de Datos (backend/etl/sync_service.py)

El proceso ETL transforma documentos NoSQL desnormalizados a un esquema relacional estricto:

1. Extracción Diferencial (Extract)
Solo consulta documentos con sync_status != 'SYNCED'. Esto evita reprocesar millones de registros históricos y minimiza el uso de CPU y ancho de banda.
2. Transformación a 3FN (Transform)
Desempaqueta el documento JSON de MongoDB:
  • El objeto cliente se normaliza en la tabla clientes (evitando duplicados por email).
  • La orden se inserta en pedidos registrando el _id de Mongo en la columna mongo_id.
  • El arreglo productos se desglosa en filas individuales en productos y detalle_pedido con sus claves foráneas.
3. Carga Idempotente (Load)
Utiliza sentencias SQL con protección de conflicto: 
INSERT INTO pedidos (cliente_id, fecha_orden, mongo_id, cluster_origen, total, estado, sincronizado_en)
VALUES (%s, %s, %s, %s, %s, 'CONFIRMADO', NOW())
ON CONFLICT (mongo_id)
DO UPDATE SET total = EXCLUDED.total, sincronizado_en = NOW()
RETURNING id;
4. Cierre y Auditoría
Al recibir la confirmación de PostgreSQL, MongoDB actualiza el documento a "sync_status": "SYNCED" y el servicio registra un log en la tabla sync_logs de Neon (registros extraídos, cargados, milisegundos y estado).

5. Guion de la Demostración en Vivo (Paso a Paso)

  1. Iniciar Servidor: Ejecuta python main.py dentro de backend/.
  2. Oficina Virtual: Abre en tu navegador http://localhost:8000/oficina (o /dashboard).
    • Muestra a los Bots 1, 2 y 3 trabajando sobre el Clúster 1.
    • Presiona el botón de "5 Bots". Muestra cómo los Bots 4 y 5 se activan y empiezan a enviar transacciones directamente al Clúster 2.
  3. Verificación en MongoDB Atlas:
    • Abre la consola de MongoDB Atlas y entra al Clúster 2.
    • Entra a Browse Collections: muestra la base neondb y la colección pedidos.
    • Muestra un documento recién insertado: apunta a los evaluadores que su campo es "sync_status": "PENDING".
  4. Disparo del ETL:
    • En la Oficina Virtual, da clic al botón "Sincronizar Ya".
    • Señala que el indicador de estado pasa a amarillo ("ETL en ejecución") y regresa a verde ("Sincronizado").
    • Refresca MongoDB Atlas: el documento cambió a "sync_status": "SYNCED".
  5. Verificación en PostgreSQL Neon:
    • En el SQL Editor de Neon, ejecuta la consulta de comprobación: 
      SELECT id, mongo_id, cluster_origen, total, sincronizado_en 
FROM pedidos 
ORDER BY id DESC LIMIT 5;
    • Comprueba que el mongo_id coincide con el _id del documento de MongoDB.
    • Ejecuta la consulta de auditoría: 
      SELECT * FROM sync_logs ORDER BY id DESC LIMIT 3;

6. Banco de Preguntas Trampa de los Profesores

P1: ¿Por qué no había base de datos ni tablas en el Clúster 2 al principio?
Respuesta: En MongoDB rige el principio de Lazy Creation (creación perezosa). Las bases de datos y colecciones no se crean mediante DDL (como CREATE DATABASE), sino que se inicializan físicamente en disco en el milisegundo en que se ejecuta la primera inserción (insert_one) derivada de los bots del rango 4 al 6.
P2: ¿Cómo garantizan que PostgreSQL y MongoDB tienen la misma información?
Respuesta: Mediante el modelo de Consistencia Eventual. MongoDB asume la ingesta inmediata con PENDING. El ETL periódico lee en lotes diferenciales y solo tras un commit exitoso en Neon actualiza el estado a SYNCED en Atlas. Si ocurre un fallo de red, la transacción no se pierde y se reintenta en el próximo ciclo gracias a la cláusula ON CONFLICT (mongo_id) (idempotencia).
P3: ¿Cómo consultan los índices de las bases de datos?
En MongoDB: db.pedidos.getIndexes(); (índice único en _id).
En PostgreSQL Neon: SELECT tablename, indexname, indexdef FROM pg_indexes WHERE tablename = 'pedidos'; (índice único en mongo_id para búsquedas O(1)).
P4: ¿Cómo se manejó la seguridad y los roles de usuario?
Respuesta: Aplicando el principio de menor privilegio. En MongoDB Atlas se crearon roles dedicados: mongo_developer (lectura y escritura acotada únicamente a la base neondb) y mongo_user (solo lectura para auditoría). En Neon se utiliza autenticación cifrada mediante canal seguro SSL (sslmode=require).
